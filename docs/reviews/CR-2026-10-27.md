## P0 阻断项（必须修复后才能继续推进）

### B1 代码从未通过类型检查：`tsc` 报 18 个错误

`packages/core/tsconfig.json` 启用了 `noUncheckedIndexedAccess: true`，而 `sort.ts` 全程按"数组下标一定存在"写。实测输出（截取）：

```
sort.ts(37,13)  error TS2532: Object is possibly 'undefined'.
sort.ts(39,3)   error TS2322: Type 'number | undefined' is not assignable to type 'number'.
sort.ts(57,23)  error TS18048: 'single' is possibly 'undefined'.
sort.ts(67,36)  error TS2532: Object is possibly 'undefined'.
sort.ts(81,34)  error TS18048: 'plane' is possibly 'undefined'.
sort.ts(96,7)   error TS2322: Type 'ImagePlane | undefined' is not assignable to type 'ImagePlane'.
sort.ts(116,27) error TS2532: Object is possibly 'undefined'.
sort.ts(126,11) error TS18048: 'dist' is possibly 'undefined'.
sort.ts(145,57) error TS2532: Object is possibly 'undefined'.
```

**18 个错误全部集中在 `sort.ts`**，`lut.ts` / `vector3.ts` / `ports` / `domain` 干净。

典型位置：

| 行 | 代码 | 问题 |
| --- | --- | --- |
| 56-57 | `const single = planes[0]; single.sliceThickness` | `planes[0]` 是 `ImagePlane \| undefined` |
| 67 | `planes[0].imageOrientationPatient` | 同上 |
| 80-81 | `const plane = planes[i]` | 循环下标同样受影响 |
| 116 | `projectables[i + 1].projection` | 同上 |
| 124-129 | `sliceDistances[i]` | `number \| undefined` |
| 145 | `sortedPlanes[0].sliceThickness` | 同上 |

**这不是"加个 `!` 就行"的问题。** 加非空断言会掩盖真实风险：`planes[0]` 在数组为空时确实是 `undefined`（虽然上面有 `length === 0` 早退，但类型系统不认这种跨行推断）。正确做法是**用局部变量收窄 + 边界判断**，而不是断言。

**根因**：写代码时没有跑 `tsc`。这件事必须在提交前自动化，不能靠自觉。

**修复**：
1. 补 `devDependencies: { "typescript": "^5.6" }` 与 `"typecheck": "tsc --noEmit -p ."` 脚本。
2. 逐处用收窄写法重写（示例见文末附录 A）。
3. **加 CI 门禁**：`tsc --noEmit` 不过不许合并。

## P1 严重项

### S1 窗宽窗位映射口径偏离 DICOM 标准（数值正确性问题）

`lut.ts:36-42` 与 `types.ts:107-110` 两处一致地写成：

```ts
lower = windowCenter - windowWidth / 2
upper = windowCenter + windowWidth / 2
```

DICOM PS3.3 C.11.2.1.2 线性 VOI LUT 的定义是：

```
y = ymin                             当 x ≤ c - 0.5 - (w-1)/2
y = ymax                             当 x > c - 0.5 + (w-1)/2
y = ((x - (c-0.5))/(w-1) + 0.5) · (ymax - ymin) + ymin
```

即下界 `c - 0.5 - (w-1)/2`、上界 `c - 0.5 + (w-1)/2`，**不是** `c ± w/2`。

**实测差异**（脑窗 ww=80 / wc=40）：

| HU | 当前实现 | DICOM 标准 | 差 |
| --- | --- | --- | --- |
| 0 | 0 | 0 | 0 |
| 40（窗位） | 128 | 128 | 0 |
| **79** | **252** | **255** | **-3** |
| 80 | 255 | 255 | 0 |

窗宽越大差异越小，窗宽越小越明显。**视觉上几乎看不出，但 ARCHITECTURE.md §12 要求"像素级 golden test，容差 0"**——这个口径不改，基准图永远对不齐，最后一定会有人去"调容差"，把正确性底线调没了。

**修复**：`voiToRange` 改为标准公式；`mapHUToUint8` 改为标准三段式；`VOIBounds` 的注释同步纠正（现在注释也是错的，属于"错得一致"）。

### S2 `ModalityLUTSequence` 完全未实现

`lut.ts` 只有 `rawToHU(pixel, slope, intercept)`，走的是 Rescale 路径。§5.2 明确要求"存在 `ModalityLUTSequence` 时查表"。

**影响**：部分 CR/DX/乳腺机型的 HU/OD 换算直接读取 LUT 表，只做线性换算会得到系统性错误的数值。且这类数据在国产设备上并不罕见。

**修复**：`ImagePlane` / `PixelFrame` 增加 `modalityLut?: { firstMappedPixelValue: number; bitsStored: number; data: Uint16Array }`，`rawToHU` 改为 `applyModalityLut(pixel, plane)` 优先 LUT、回退 Rescale。

### S3 `MONOCHROME1` 未处理

`types.ts` 定义了 `photometricInterpretation` 字段，但 `lut.ts` 的 `mapHUToUint8` 没有反转逻辑。`MONOCHROME1`（高值显黑）在 CR/DX 中常见，不反转则**整幅图明暗颠倒**——这是医生一眼就能看出的错误，也是最伤信任的那类 bug。

### S4 缺层检测算法脆弱，存在静默失效路径

`sort.ts:113-140` 用"相邻距离的中位数 × 1.5"判定缺层。三个问题：

1. **中位数会被缺层本身污染**。若一个序列 50% 的层被丢掉，中位数被拉高到 2×，此时 `1.5 × 2×` 的门槛刚好漏掉所有缺层——**越该报警的数据越不报警**。
2. **重复层会把中位数拉到 0**。`dist = 0` 进入 `sliceDistances` → `medianSpacing` 可能为 0 → 第 122 行 `if (medianSpacing > 1e-4)` 判断失败 → **整个缺层检测被跳过，且不产生任何 warning**。这条直接违反 R7（禁止静默降级）。
3. **只检测"偏大"，不检测"偏小"**。层距为中位数 0.3 倍的重叠层不会被发现，而 `DataWarning` 里已经定义了 `IRREGULAR_SPACING`，实现中**从未产生过这个 code**。

**修复建议**：

- 优先用 `spacingBetweenSlices ?? sliceThickness` 作为期望层距（元数据可信时）；缺失时才回退统计量。
- 统计量用**众数（mode，按 0.1mm 分桶）**而非中位数，抗污染。
- 先过滤 `dist < 1e-3` 的重复层并单独产生 `DUPLICATE_SLICE` 警告（需在 `DataWarning` 增补 code）。
- 双向判定：`dist > 1.5×` 报 `SLICE_GAP`，`dist < 0.7×` 报 `IRREGULAR_SPACING`。

### S5 `ORIENTATION_MISMATCH` 只告警，不改变行为

`sort.ts:85-92` 检测到法向量夹角余弦 < 0.95 时 push 一条 warning，但**仍然把这层和其他层混在一起按投影排序**。

**后果**：混合体位的序列会被排成一个"看似正常的序列"，MPR 重建出来是扭曲的。这比直接报错危险——用户看到的是"一张有点怪的图"，不是"一个明确的错误"。

**修复**：朝向不一致的切片应**从主序列剔除**，归入独立的 `excludedPlanes`，并产出一条 `error` 级 warning 说明"发现 n 层与其他层体位不一致，已排除，请检查是否混合了不同序列"。

### S6 Gantry Tilt / 非轴对齐朝向未检测

§7.4 要求处理机架倾斜。当前 `sort.ts` 完全没有相关逻辑，`DataWarning` 也没有对应 code。

**修复**：计算基准法向量与三个设备轴（±x/±y/±z）的最大夹角余弦，若 < 0.999 则产出 `NON_AXIAL_ORIENTATION` 警告（severity: warning），提示"该序列为斜位/倾斜采集，MPR 重建需 affine 校正"。**这是告警而非错误**——斜位采集本身合法，但下游必须知道。

### S7 `CodecPort.decode` 返回值信息不足，上层无法正确构造数据

```ts
decode(...): Promise<{ data: Int16Array | Uint16Array | Uint8Array; width: number; height: number }>
```

缺 `bitsAllocated`、`pixelRepresentation`、`photometricInterpretation`、`rescaleSlope/Intercept`。

**后果**：调用方拿到一个联合类型数组，既不知道该怎么解读，也不能安全地转成 `PixelFrame`——只能靠猜或再查一遍元数据，把职责割裂成两处。

**修复**：返回值直接返回 `PixelFrame`（`domain/types.ts` 已有定义），把 `rescaleSlope/Intercept/defaultVOI` 一并带出。端口返回值应该是领域对象，不是元组。

## 附录 A：类型收窄的正确写法（替代 `!`）

// ❌ 当前：tsc 报错
const single = planes[0];
const thickness = single.sliceThickness ?? 1.0;

// ✅ 收窄后：类型安全，且比 ! 更能防真实越界
const [first] = planes;               // first: ImagePlane | undefined
if (!first) {

// ❌
for (let i = 0; i < planes.length; i++) {

for (const plane of planes) {        // 迭代器天然无 undefined
