## 一、P0-1 开发模式下视口完全挂载失败（StrictMode + 生命周期归属倒置）

### 实测证据

同一份代码，开发模式与生产构建的结果**完全相反**：

```
# 开发模式（vite dev，端口 3001）
$ chrome --headless --dump-dom http://localhost:3001/
canvas 数量: 0
CONSOLE: "渲染器挂载失败: Error: 渲染器已销毁，不能复用；请重新创建实例"   ← Viewport.tsx:54
CONSOLE: "渲染器挂载失败: Error: mount 过程中渲染器被销毁，本次挂载未生效"

# 生产构建（vite build + preview，端口 4321）
$ chrome --headless --dump-dom http://localhost:4321/
canvas 数量: 1        ← 正常
```

`main.tsx:12` 用了 `<StrictMode>`，React 19 在开发模式下会**双调用 effect**：
mount → cleanup → mount。而 `Viewport.tsx:60-64` 的 cleanup 里调了 `renderer.destroy()`：

```ts
return () => {
  mountedLocally = false;
  renderer.destroy();   // ← 销毁的是 App 持有的共享实例
  setIsMounted(false);
};
```

第二次 mount 撞上 `RendererPort` 的 `assertAlive()`，抛错被 `catch` 吞成 `console.error`，
`setIsMounted(true)` 永远不会执行 → 视口区只剩占位文案，**开发全程白屏**。

### 根因不是 StrictMode，是所有权倒置

`renderer` 由 `App.tsx:15-19` 的 `useMemo` 创建并持有，却由子组件 `Viewport` 销毁。
谁创建谁负责销毁；而且以后做多视口（2×2）时，4 个 `Viewport` 会互相踩同一个 engine。

### 整改要求

1. **`mount` / `destroy` 上提到 App**：App 的 effect 里 `renderer.mount(...)` 一次（带完整 layout），
   cleanup 里 `renderer.destroy()`；`Viewport` 只拿 `viewportId`，做 `setStack` / `setStackIndex`，
   卸载时最多调 `renderer.disposeViewport(viewportId)`。
2. 或者让渲染器支持"销毁后可重建"（`destroy()` 后 `mount()` 重新建 engine）。**二选一，不要两边都留半截。**
3. 无论选哪种，**mount 失败必须给用户可见提示**（见 P1-1），不能再只有 `console.error`。

> 附带发现：我的 `mount` 竞态检测在这里救了一次——它把"销毁后才挂载完成"显式抛了出来，
> 否则会静默拿到一个半死的 engine。这说明上一轮的版本号机制是有用的。

## 二、P1 清单

### P1-1 渲染/装载失败对用户完全不可见（违反 R7）

`Viewport.tsx:54` 与 `:97` 两处失败路径都只 `console.error`。用户看到的是纯黑视口，
不知道是"DICOM 损坏""格式不支持"还是"引擎崩了"。R7 要求所有失败路径有用户可见提示。

**要求**：把这两类错误写进 store（如 `importStatus.error` 或新增 `viewportError`），顶部红色横条已有现成样式可直接复用。

### P1-2 序列枚举绕开端口，UI 绑死具体适配器

`SeriesList.tsx:2` 直接 `import type { LocalDataSource }`，props 类型是**具体类**：

```ts
interface SeriesListProps { readonly dataSource: LocalDataSource; }
```

而 `listSeries()`（`source-local.ts:180`）是新增在**具体类**上的方法，不在 `DataSourcePort` 里。
同时 `Header.tsx` 的 props 是 `DataSourcePort` —— 同一个数据源在两个组件里两种类型。

连锁问题：因为端口没有"列序列"能力，`probe()` 只返回 `StudyMeta[]`（含 `seriesCount`），
UI 拿不到序列清单，于是 `Header.tsx:48` 用 `seriesInstanceUid: ''` 让适配器"挑第一个"：

```ts
seriesInstanceUid: '', // 传空字符串由 dataSource 选择首个序列
```

而 `source-local.ts` 为此把匹配逻辑改成了 `(!ref.seriesInstanceUid || s.seriesInstanceUid === ref.seriesInstanceUid)` ——
**空字符串成了通配符**。这会静默吞掉调用方的传参错误（本来该报"找不到序列"，现在随机选中第一条）。

**要求**（按此顺序）：
1. 在 `DataSourcePort` 增加 `listSeries(studyUid): Promise<readonly SeriesSummary[]>`（**改 core 端口，需过我评审**）；
2. `SeriesList` 的 props 改回 `DataSourcePort`，删掉对具体类的 import；
3. 撤销 `openSeries` 的空串通配行为，恢复"找不到就报错"——`SeriesRef` 的两字段都是必填，缺一个就是调用方 bug。

### P1-3 两处 `as` 硬转，违反 GEMINI §10

| 位置 | 代码 | 问题 |
| --- | --- | --- |
| `bridge/cs3d-bridge.ts:171` | `} as unknown as cs3d.Types.IImage;` | **§10 明令「`as unknown as X` 一律打回」** |
| `bridge/cs3d-adapter.ts:95` | `const type = options.type as cs3d.Enums.ViewportType;` | 把 `string` 裸断成枚举 |

`IImage` 是 CS3D 的公开类型且本包已安装 CS3D，可以老老实实逐字段满足（`getPixelData` 的返回类型、
`dataType` 用联合类型而非字符串、`voiLUTFunction` 直接取枚举值）。`Cs3dModuleLike.Enums` 也可
在端口层就声明为 CS3D 的枚举类型，而不是 `string`。

> 这两处正是"依赖倒置生效"与"用断言糊过去"的分界线。前者我上一轮刚表扬过，别在这里破功。

### P1-4 `frameOfReferenceUID` 用 StudyInstanceUID 冒充

`bridge/cs3d-bridge.ts:86`：

```ts
return buildImagePlaneModule(plane, handle.meta.studyInstanceUid);
```

`frameOfReferenceUID` 与 `StudyInstanceUID` 是两个完全不同的概念。同一个 Study 下若有多条
不同 FrameOfReference 的序列（复查、不同体位），会被判成同一坐标系，MPR / 融合 / 配准会静默错位。
而且这个字段一旦被下游当真，排查成本极高。

**要求**：`frameOfReferenceUID` 缺失时**留空或按序列派生（如 `${seriesUid}.for`）并显式标注为合成值**，
绝不能借 Study UID。若 CS3D 强制要求非空，就在 Adapter 注释里写明"合成值，仅用于满足接口"。

## 四、值得肯定的部分（这几条是真本事）

1. **ADR-013 兑现得干净**：产物里 **0 个 wasm**、主包 gzip 428 KB。对比 Spike A 里引入
   `dicom-image-loader` 的 1.45 MB + 1.98 MB wasm —— 自定义 `odv://` loader + `metaData.addProvider`
   这条路走通了，§11 的包体积预算第一次有了实测支撑。
2. **R4 守住了**：滚轮翻页与右键调窗全部用 `useRef` + 直接改 `textContent`，没有一次 setState。
   这是最容易破功的一条，实现得很克制。
3. **零外部请求**：`index.html` 的 CSP 是 `default-src 'self'`，产物里除注释里的 kitware 版权链接外
   没有任何外部资源，也没有 `@font-face`。
4. **`cs3d-adapter.ts` 用包装类而非类型断言**把 `IStackViewport` 收窄进 `Cs3dViewportLike`，
   这个思路是对的——只有 `IImage` 那一处破例（P1-3）。
5. **app-web 的 16 条用例是真用例**：`bridge.test.ts` 断言了 `computeMinMax`、IOP 解构、
   Range 读取、AbortSignal、loader 注册回调；`store.test.ts` 断言了旧句柄释放与 reset 清理。
   都 import 了真实实现，不是手抄期望值。
