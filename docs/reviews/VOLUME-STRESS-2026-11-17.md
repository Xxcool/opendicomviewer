# 千帧导入与重复体渲染验收 · 2026-11-17

本机为 Apple M1、16 GiB、macOS 15.1.1。用 Playwright 驱动本地生产 Web 构建，分别运行 Chrome 156 和 Playwright WebKit。每次读取实际画布，将其缩到 64 × 64 统计灰度值，要求每个视图都有非黑像素，并比较旋转前后的像素哈希。该 WebKit 结果对应自动化运行时，尚需在目标 iPad 上复验。

| 序列和操作 | Chrome | WebKit |
| --- | --- | --- |
| 193 层 ICBM 示例，连续十轮从首页打开、查看原图和四视图 MPR、进入 3D、旋转、返回首页 | 十轮均出像，旋转后图像变化 | 十轮均出像，旋转后图像变化 |

千帧输入为 525,549,550 字节的合成序列。自动化计时包含选择文件、状态等待和画布检查，同台单次测量只代表本轮条件。

## 内存

Chrome 十轮 193 层测试中，显式 GC 后的活动视图数组后备存储每轮均为 32.2 MiB，JS 堆已用量由首轮 8.8 MiB 到第十轮 11.5 MiB。回首页保留活动会话，以支持继续阅片。测试过程中发现首页遮挡设置对话框，修复后从首页实际点击「清空会话」成功。

在额外开启跨源隔离与 Chrome `ForceEagerMeasureMemory` 的本地服务上，对千帧运行约每 100 ms 发起一次 `measureUserAgentSpecificMemory()`。58 次采样的最大页面内存为 104.0 MiB。这次原图就绪用时 3.808 秒。另一次普通运行中，系统 RSS 记录到渲染进程最高约 559 MiB，GPU 进程约 163 MiB，整个浏览器进程树合计最高约 1224 MiB。这些指标的统计范围不同。页面采样间隔可能遗漏瞬时峰值，系统 RSS 包含浏览器自身和共享映射，此次没有独立测量 GPU 显存。

## 复验方法

1. 运行 Web 生产构建并在本机启动预览。使用内置头部 MR 检查上述十轮操作，确保从首页重新打开以替换活动会话。
2. 从仓库的 `sample-dicom/brain-head-mr/head-axial-096.dcm` 复制非像素元数据，用 pydicom 生成一个新 Study、Series 和 Frame of Reference，设为 512 行、512 列。生成 1000 个独立 SOP 实例，实例号 1 到 1000，位置为 (0, 0, z)，z 从 0 到 999。设置 slope/intercept = 1/0、窗宽/窗位 = 300/100。使用 int16 小端像素，绘制以 (256, 256) 为中心、像素值 180 的圆盘，背景为 0，半径为 135 + (z 整除 20) 对 80 取余。每个 SOP 同步其文件元信息 UID。
3. 用查看器的文件夹入口载入生成序列，核对总层数和末层，再切到 MPR 和 3D。监测页面内存时为本地资源提供 COOP same-origin、COEP require-corp，并记录浏览器启动选项、采样间隔和归属范围。

此次验证覆盖上述灰阶序列、桌面硬件与浏览器引擎。压缩传输语法、其他 GPU、移动设备和长时间临床工作负载仍需单独验证。
