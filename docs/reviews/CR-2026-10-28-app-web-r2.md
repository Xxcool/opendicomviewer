## 一、P0 复核：真修（附实证）

**整改前**（上轮实测）：`vite dev` 下 `canvas 数量 0`，控制台两条
`渲染器挂载失败: Error: 渲染器已销毁，不能复用` / `mount 过程中渲染器被销毁`。

**整改后**（本轮实测，同一命令）：

```
$ npx vite --port 4322 &  # 开发模式
$ chrome --headless --dump-dom http://localhost:4322/
canvas 数量: 1
失败相关控制台: （空）
```

**修法核对**：`App.tsx:26-62` 把生命周期上提，且关键点是
**渲染器在 effect 内部 `createCornerstoneRenderer(...)`**，cleanup 里 `r.destroy()` 并把
`renderer` 置 null。StrictMode 双调用时每次拿到的是**全新实例**，不再撞 `assertAlive()`。
`Viewport` 只接收 `renderer: CornerstoneRenderer | null`，不再 mount/destroy。

这是"结构上正确"的修法，没有靠去掉 StrictMode 或加 try/catch 糊过去。

## 四、本轮新发现（整改引入，需处理）

### 新增-1（P1，流程）：零新增测试

用例总数与整改前**完全一致**：94 条；`app-web/tests` 两个文件行数一字未变（134 / 106）。

后果：**P0 的修复没有任何自动保护**。任何人把 `destroy()` 挪回子组件、或去掉 effect 内的
重新创建，`vite dev` 又会白屏——而 CI 只跑 vitest，**永远绿**。上一轮 P0 就是这么溜进来的。

**最低要求**（提交前补，按成本从低到高）：

1. 一条 dev 冒烟脚本（`scripts/smoke-dev.mjs` 或 vitest 里的独立 case 调用 Chrome）：
   起 dev → `--dump-dom` → 断言 `canvas` 数量为 1 且输出不含 `渲染器挂载失败`；
2. `openSeries` 空 UID 抛错用例（source-local，2 行）；
3. `listSeries` 单测（含 DICOMDIR 与非 DICOMDIR 两条路径的 `numberOfFrames` 取值差异）；
4. FoR UID 派生用例（`buildImagePlaneModule` / provider 返回 `${seriesUid}.for`）。

### 新增-2（P2）：滚轮路径重新引入 setState，且与 ref 双写

`Viewport.tsx:109` 在 wheel 回调里 `setSliceIndex(nextIndex)`，紧接着 `:110-115` 又用
`sliceTextRef.current.textContent` / `sliderRef.current.value` 手写 DOM；而 `:275` 的显示
是由 `sliceIndex` 渲染的。

两个问题：
1. **每次滚轮都触发一次 React 重渲染**（整棵 Viewport 子树），正是上一轮我表扬 R4 时说的"绝不能进"的那条路径；
2. **双写互相覆盖**：React 重渲染会用 state 覆盖手写 textContent，滚动够快时容易出现显示回跳。

**要求二选一**：①回到纯 ref 方案（`sliceIndex` 只做 ref，滑块 `defaultValue` + 手动同步）；
②彻底 state 驱动，删掉 `:110-115` 的 ref 双写。**不要两套并存。**

### 新增-3（P3）：无谓 `as`

`source-local.ts:183` 与 `:201` 的 `(s.modality ?? 'OT') as SeriesSummary['modality']` ——
`Modality` 已包含 `(string & {})` 分支，`string` 本来就可赋值，这个断言是空转。
去掉即可（少一处 `as`，少一次"这里为什么要断言"的疑问）。

### 新增-4（P3）：CS3D 被 pnpm 装成 renderer-cs3d 的真依赖

`pnpm-lock.yaml` 的 `packages/adapters/renderer-cs3d` importer 里出现
`@cornerstonejs/core: 4.22.13` —— 我上一轮标的 `peerDependenciesMeta.optional` 没生效
（pnpm 9 的 `auto-install-peers` 照装）。ADR-013 的"单测无需安装 CS3D"因此只在**单独安装该包**时成立。

**处置建议**：要么把它从 `peerDependencies` 挪到 `devDependencies` 并注明"仅供类型与联调"，
让 lock 与实际一致；要么接受现状并修订 ADR-013 的措辞。**不要让 manifest 和 lock 说两套话。**
